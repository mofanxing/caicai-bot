# 菜菜插件式 Agent 调度架构

记录日期：2026-11-17（Asia/Shanghai）。

状态：用户已确认产品方向和架构边界；M1 已新增固定上游版本的桌宠底座、控制面板与正式桌面聊天，流式文字、分段语音和真实状态动画已接通并完成隔离链路验收，见 [桌面端说明](../desktop/README.md)。Python 后端自动启动、外部服务复用、故障提示和退出清理已实现并通过隔离验收；完整人工交互、双角色实测与打包尚未完成；插件系统和执行器尚未接入。本文插件契约字段和调度目录结构仍为实施建议，开发前按实际执行器能力细化。

## 1. 已确认的产品目标

将菜菜做成以桌宠为入口、通过插件扩展能力的个人 Agent 调度平台。用户通过文字、未来通过语音交代工作；菜菜理解需求、选择 Agent、建立任务、展示进展并交付结果。

- 桌宠在 dsh-pet 项目基础上修改，必须保留其动画交互与角色切换能力，并保留低成本、快速新增角色的制作与接入流程；这是选择该上游的核心原因，也是首版要求。
- 保留菜菜现有 FastAPI + SQLAlchemy + SQLite 后端和 React 管理前端，复用模型配置、聊天、音色与本地语音。
- 调度能力采用插件模式，Codex 和 DeepSeek Harness 均作为计划接入的执行器；首个执行器的具体选型、版本及接口尚未确定。
- 新增业务能力优先通过 Agent 配置、执行器适配器和工具插件完成，避免为每一种业务修改桌宠和调度核心。
- 先实现单 worker、单任务并发和一个真实执行器；多执行器并发、复杂多 Agent 协作后置。
- 微信接入继续后置；桌宠不依赖微信。

## 2. 概念与职责

| 概念 | 职责 | 示例 |
| --- | --- | --- |
| Agent | 定义角色、目标、处理流程、执行器选择及允许使用的能力 | 编程 Agent、资料整理 Agent、日程 Agent |
| 执行器 | 运行 Agent 的工具调用循环，管理实际执行过程 | Codex、DeepSeek Harness、未来自建执行器 |
| 工具插件 | 提供具体操作能力，声明输入、输出和权限 | 文件读写、运行测试、日历接口 |
| 插件包 | 注册并交付一组 Agent、执行器适配器或工具能力 | 编程插件可以同时带 Agent 定义和执行器适配器 |
| 调度核心 | 校验请求、路由 Agent、持久化任务、管理执行状态与结果 | 派发任务、显示进度、处理确认和取消 |
| 桌宠与工作台 | 接收输入、展示聊天和任务、呈现动画与提醒 | 思考、执行、等待确认、成功、失败 |

当执行器已支持需要的工具时，新增 Agent 可以主要依靠配置；新工具、新外部系统或新执行器通常仍需要适配代码。提示词不会自动产生文件、网络或系统操作权限。

工具既可以由执行器原生提供，也可以通过其支持的扩展机制接入。第一版不要求菜菜统一重写或代理所有工具；适配器必须明确实际支持和可约束的能力。

## 3. 建议架构

```text
桌宠（基于 dsh-pet） / 聊天窗 / 管理工作台 / 未来微信
                          │
                  菜菜对话与任务入口
                普通聊天 / 任务请求 / 补问
                          │
                    菜菜调度核心
           任务、执行尝试、进度事件、确认与结果
                          │
                     插件注册中心
                          │
           ┌──────────────┼──────────────┐
        编程插件       资料整理插件      日程插件
           │              │              │
      Codex / DSH      执行器与工具     日历与提醒接口
        执行器适配器
                          │
                 独立 worker / 执行进程
```

所有入口复用同一套任务服务。任务状态保存在后端，不依赖聊天上下文或窗口生命周期。桌宠收起后任务继续；整个程序退出或执行进程中断后，应识别中断状态，不盲目重放有副作用的操作。

第一版优先复用成熟执行器的执行循环，不先自建通用工具调用框架。模型负责理解和规划，模型生成的 Agent 选择、工具参数和目录必须经过服务端校验。

## 4. 最小插件契约（建议）

### 声明与注册

插件声明建议至少包含：唯一 ID、版本、插件契约版本、名称与用途、提供的 Agent、输入 schema、所需执行器与工具、权限需求、配置 schema，以及能力标记。

- Agent 声明自身适用任务及所需能力，执行器适配器声明实际支持的能力；派发前检查匹配。
- 本地显式注册和启用优先，暂不做插件市场、在线安装或热加载。
- 配置中的密钥使用后端已有的保护机制，不把真实密钥写入插件清单或桌宠渲染页面。
- 插件启用时检查依赖、配置与可用性，未就绪时明确报错，不显示为可执行。
- 加载第三方代码意味着信任该代码；声明权限本身不等于具备隔离能力，具体约束必须落实到实际执行边界。

### 执行与生命周期

| 能力 | 建议约定 |
| --- | --- |
| 检查可用性 | 检查执行器安装、必要配置和连接，返回可解释的不可用原因 |
| 启动任务 | 接收任务与执行尝试 ID、Agent、目标、受控项目目录、上下文和权限策略；保存执行器返回的运行引用 |
| 进度事件 | 统一接收排队、执行、进度、等待确认、产物及终态事件，并保存执行器原始运行关联 |
| 取消 | 标记取消请求并向实际运行传递信号；确认停止后才进入已取消，不能只更新界面 |
| 确认 | 仅对执行器支持的确认机制提供响应适配；不得自动同意敏感操作或绕过执行器限制 |
| 查询与恢复 | 重连后优先查询真实运行；执行器不支持时明确限制，将无法确认的运行标记为中断或待核查 |
| 结果 | 返回终态、说明、产物引用及验证结果；失败保留可解释原因 |

暂停、恢复、交互式确认、工具扩展等通过能力标记显式声明。不能假设所有执行器支持相同功能；不满足任务必要条件时拒绝派发或提示更换执行器。

## 5. 任务与事件记录

建议区分以下实体，具体 schema 在 M2 定稿：

- 任务：用户目标、关联会话、Agent、插件版本、项目目录、状态、结果与创建时间。
- 执行尝试：任务的某一次运行、执行器与配置引用、外部运行 ID、起止时间、退出或失败原因；重试新增尝试，保留历史。
- 进度事件：任务 / 尝试 ID、单调递增序号、事件类型、时间和经脱敏的内容，供工作台与桌宠重连补读。
- 产物：文件或其他结果引用、类型与说明，不把“模型声称完成”直接作为验证成功。
- 确认请求：关联运行、待确认操作、当前状态与实际回复；只在适配器支持时启用。

任务状态至少覆盖 queued / running / waiting_confirmation / succeeded / failed / cancelled / interrupted；取消请求可用 cancelling 中间态或独立字段表达。实施时明确合法转换和终态，保证同一任务不会同时被多个 worker 执行。

创建任务和启动执行应有幂等标识。网络重试、重复点击或重连不得隐式创建重复执行。重试可能再次产生副作用时，应显式展示，并按权限策略处理。

## 6. 与 dsh-pet、聊天和语音的衔接

- dsh-pet 上游地址：https://github.com/PC2005-cloud/dsh-pet 。正式开发前固定提交，并验证 macOS 运行；此前静态评估参考提交为 fb38ce620576f5ed3735a99536d2b1a4a9eb313f，不代表已完成真机运行或发布版本核验。
- 复用动画、透明窗口、拖拽、托盘、气泡及工作状态表现；增加菜菜后端适配层，不复制第二套模型密钥、会话和任务数据。
- 保留 dsh-pet 的角色选择与切换流程、角色素材组织和动画交互机制。固定上游版本后核实角色包格式与加载方式，记录兼容边界；新增角色优先只新增素材与必要配置，不要求修改桌宠渲染、调度核心或执行器代码，也不把 Live2D 建模作为前置条件。
- 桌宠形象与 Agent、聊天人设、音色分别配置；默认切换形象只改变表现层，不重置会话、不切换执行器、不影响正在执行的任务。角色与人设、音色的联动如后续需要，应显式配置。
- 接入菜菜状态时沿用上游动画机制；角色缺少新增状态动作时复用其已有合适动作，避免每次扩展任务状态都要求重做所有角色素材。具体映射在 M1 验证。
- 现有聊天已经具备流式文字和分段语音；新增正式 desktop 通道和接口，避免桌面产品继续依赖 debug 入口。
- 复用 VoxCPM2 本地音色复刻与分段播放器。动画依据真实状态切换：聊天生成时思考、音频待生成时等待、实际出声时说话。
- 任务进度绑定具体 task_id / attempt_id；首版只运行一个任务，仍需避免旧事件覆盖新任务。
- 聊天状态、任务执行状态和语音播放状态分别维护，再决定展示优先级，避免聊天结束把仍在执行的任务错误显示为空闲。
- 睡觉、静音、关闭气泡等属于显示与通知偏好，不隐式取消任务或批准操作；等待确认、失败和结果在工作台中持续可见。
- 明确桌宠收起、关闭聊天与退出应用的区别；后端由桌面管理或连接既有实例的方式在 M1 验证，退出和中断策略必须一致。
- 沿用管理员鉴权，核查新增本地 HTTP / IPC 的调用边界；插件或执行器日志不得泄漏凭据。
- 上游代码和形象素材的授权分别核查；保留来源与版权说明，公开分发或商用前确认所用素材许可。
